# 本地视觉跟随

入口：桌面 App → 手机工作区 → **视觉跟随**。

用 OpenCV 在小地图中匹配自己和指定队友的图标，用 A* 在校准的障碍网格上寻路，通过 ProfilePilot 手机会话持续操作摇杆。图像在电脑本机处理，无需大模型或模型 API Key。

## 没有设备时

点击 **演示地图 → 开始演示**。绿色图标会根据真实 OpenCV 返回的位置和路线移动，绕开中间墙壁。可以停止后修改障碍，再观察路线变化。该地图是合成演示，不是王者游戏实测。

也可以导入游戏截图，依次框选小地图、自己图标、队友图标，涂出障碍并分析。导入多张截图后可按选择顺序回放；回放不会操作手机。

## 连接设备后

1. 更新到包含此功能的手机开发版，连接 ProfilePilot，开启所需的无障碍与控制状态权限，结束已有手机会话。
2. 在训练或自定义对局中打开横屏游戏，点击 **获取手机画面**。
3. 框选完整小地图，再紧贴边缘框选自己的图标和指定队友的头像。图标必须能够区分；相似或重叠头像可能无法可靠识别。
4. 在小地图上涂出不可行走区域；**绕墙留白**控制额外避让范围。当前需要手动标记，不会自动理解游戏地形。
5. 点击 **摇杆中心**后在画面上点选固定摇杆中心，调整半径、方向角度、跟随距离，保存校准。
6. 先点击 **仅观察手机**检查识别与路线，再停止观察，点击 **开始跟随**。需要实机校准地图方向与摇杆方向的关系；不能假定所有游戏、分辨率和布局都相同。
7. 桌面停止、关闭跟随窗口、手机暂停/结束或会话改变都会终止跟随。默认断线也会停止；CLI 可显式选择下文的有限连接恢复，但不会恢复手机上主动暂停的会话。

App 模式只使用小地图识别时，手机按原始像素裁取小地图后压缩并传回，减少无关画面占用的传输量。返回的 `width` / `height` 仍为完整屏幕尺寸，`region` 是编码图像在原屏幕内的整数像素范围；摇杆坐标与校准方案不变。桌面预览仅显示当前小地图，停止后需要重新获取完整手机画面才能重新框选校准。启用 `nearby`、`targetPartial`、`cameraAssist` 或 `selfCameraAssist` 时需要完整场景或顶部存活提示，继续传全帧；basic 模式和旧配套 App 的普通全帧返回也保留兼容，但相机辅助还要求下述新能力。区域越界、图像尺寸不符或未覆盖完整小地图都会拒绝分析，不据此移动。

Android 11 以下的模拟器可在**控制方式**中明确选择**免安装 · 分段移动**，无需安装手机 App。此模式沿用 basic 会话，每次拖动最多 350 ms，完成后释放，再获取画面；暂停后不会提交新动作，已提交的短拖动可能完成。移动速度受截图和传输延迟影响，不能等同于手机 App 的连续触控。某些模拟器的直接截图流会截断，桌面会校验完整 PNG，并在同一有效会话中通过临时文件重新截图。

识别丢失、匹配不唯一、连续帧未确认、没有路线或位置卡住时不发送移动方向。App 模式触控带有最长 1.5 秒有效期，当前发送值为 1.2 秒；没有新指令时自动松开。App 模式单帧处理超过 1 秒、basic 模式超过 3 秒时跳过该帧移动。当前截图循环默认间隔 400 ms；App 模式通常从上次截图响应完成后计时，避免 Wi-Fi 请求延迟波动压缩手机实际收到的两次截图间隔。完整画面分块传输时，从电脑收到有效截图描述符的本地单调时间起计时，让后续分块下载计入间隔；只认可同一已完成图片对象的内部时间记录，不采用手机时钟或 JSON 时间字段。小地图、旧配套 App 和 basic 的原有节拍保持不变，移动仍按整个截图请求开始后的一秒时限判断。视觉分析和触控耗时计入这段等待，basic 模式仍按循环开始时间计时。实际帧率在界面显示，受手机截图与传输速度限制，并非 20 FPS 视频流。

连续识别允许 App 模式最多 1.5 秒、basic 模式最多 4 秒的帧间隔；间隔更长时需要重新确认目标。这个间隔只决定是否保留识别历史，不会放宽上述单帧移动时限。低帧率时会延长位置历史的保留时间，以便卡住检测仍能积累四次观察。

近期可靠位置用于缩小下一帧的搜索范围；局部匹配不足时重新搜索完整小地图，不把历史位置当作当前检测结果。短暂遮挡时仍松开摇杆，但在允许的帧间隔内保留身份确认，避免恢复识别后额外停一帧；长时间丢失或位置突变需要重新确认。路线方向会在网格中向前选取可直达的路径点，检查墙壁和斜角后再转向；接近目标后的距离滞回减少临界位置反复启停。

运行中的 App 跟随任务每秒检查并独立同步手机会话，避免截图、设备发现或其他设备轮询拖慢手机心跳；同一任务的心跳请求不会重叠。默认情况下，没有被更新成功响应取代的心跳失败会结束任务。手机会话变化始终会结束任务，不重放输入。电脑本地任务保活与手机会话续期是两个不同环节。

Windows 已安装的腾讯手游助手可通过 `ppilot phone emulator-list` 列出的 `Tencent_GameLoop` 连接；该入口复用或启动默认 100 号引擎，验证其本机调试端口和窗口位置。手游助手要求管理员权限，首次启动可能出现 Windows 授权弹窗；ProfilePilot 本身保持普通权限。连接不会安装 App 或开启控制会话。macOS 不显示此 Windows 引擎。

## 视觉运行环境

需要 Python 3.10+，以及 OpenCV、NumPy。界面会检查已安装环境；**安装视觉组件**在 App 数据目录建立独立虚拟环境，安装 `opencv-python-headless==4.12.0.88` 和 `numpy==2.2.6`。使用 Python 3.10–3.13 可匹配这组固定依赖的预编译包。未安装 Python 时先安装 Python，再重启 App。

Windows 查找 `python` 和 `py -3`，macOS 查找 `python3`；也可用 `PROFILEPILOT_PYTHON` 指定解释器绝对路径。运行时优先使用 App 自己的视觉虚拟环境。打包版本将 Python 脚本放在 `app.asar.unpacked/public/vision`。

## CLI

```text
ppilot phone follow runtime
ppilot phone follow setup
ppilot phone follow load
ppilot phone follow save --config calibration.json
ppilot phone follow start --device <实际设备ID> --config calibration.json --mode observe
ppilot phone follow status
ppilot phone follow stop --run-id <status返回的runId>
ppilot phone follow start --device <实际设备ID> --config calibration.json --mode control
ppilot phone follow start --device <实际模拟器ID> --config calibration.json --mode observe --backend basic
ppilot phone follow analyze --params-file frame.json
ppilot phone follow camera-sample --device <实际设备ID> --x <原始像素X> --y <原始像素Y> --output <新目录>
```

`start` 默认 `observe`。CLI 启动的任务由桌面 App 托管，命令退出后继续运行，直到显式停止、手机暂停/断线或 App 退出。`load` 返回 `{ ok, data }`，其中 `data` 是可保存为 `calibration.json` 的配置；`analyze` 的文件内容为 `{ "config": <配置>, "frame": { "mime": "image/png", "base64": "<不含data前缀>", "width": 1280, "height": 720 } }`。

仅 App 模式可在 `start` 追加 `--recover-transport true`，允许短暂传输中断后继续观察原会话；默认 `false`。每次断线起最多等待 2 秒，一次运行最多尝试 3 次，尝试起点至少相隔 10 秒。恢复只重建原设备地址的连接并读取状态，核对同一手机实例、会话、代次、模式和权限；不切换设备地址、不新建或恢复会话。手机已暂停、结束、锁屏或授权改变时停止。恢复后丢弃旧截图和识别历史，以新截图重新双帧确认，再决定移动；结果不明的触控不会重发，原触控仍按 1.2 秒有效期释放。状态的 `recovering` / `recoveries` 分别报告正在恢复和成功恢复次数。这是有界的容错行为，不表示无线 ADB 断线根因已修复。

配置类型见 `src/shared/game-follow.ts`。模板为 PNG 的 base64；小地图、摇杆中心和检测坐标均为 0–1 归一化坐标，摇杆半径以屏幕短边为基准。分辨率或屏幕方向改变后需要重新校准。

可选 `capture` 默认为 `auto`，只使用小地图识别时传回小地图区域；`full` 保留完整原始画面，同时仍按实际 `map` 校准分析小地图。不要为了获取全屏而把正式校准中的 `map` 改成整屏。启用 `nearby`、`targetPartial`、`cameraAssist` 或 `selfCameraAssist` 也需要完整画面，单独选择 `full` 不会自动启用这些辅助识别。

实验性 `nearby` 配置可通过 CLI 导入，用于近距离小地图头像遮挡时的辅助定位，默认不启用。`selfLabel`、`targetLabel` 是本次对局名字截图的 PNG base64，必须分别与已选择的自己及队友头像属于同一角色；`region` 是画面搜索区域，`pixelsPerMapUnit` 是画面像素位移与归一化地图位移的比例。当前只有单一比例参数，尚未完成游戏画面横纵方向比例及投影关系的实机标定，也没有自动标定或桌面框选名字入口；此功能未纳入当前整局验收配置。匹配同时检查名字下方的己方绿色或队友蓝色血条，以排除聊天文字及缺少血条的目标；这些颜色规则仍需针对其他游戏和布局验证。

辅助定位只在本帧小地图识别不足时使用：有一个可靠小地图位置且两个名字均可见时，用相对位移恢复另一个位置，随后仍按障碍网格寻路；没有可靠小地图位置时，只能确认已经足够接近并保持松手，不能据此盲目移动。分析结果的 `source` 标明 `minimap` 或 `labels`。有路径时 `distance` 为网格路径长度；无地图位置、仅确认接近时为画面换算距离，两者都以地图归一化单位表示。重新框选小地图或任一头像会清除旧名字校准，避免沿用上一目标。

可选 `selfMarker` 配置用于自己的小地图头像被部分遮挡、但专属颜色圆环仍可见的情况，默认不启用，可通过 CLI 导入。`hueMin`、`hueMax` 使用 OpenCV HSV 的 0–179 色相范围且前者不能大于后者；`saturationMin`、`valueMin` 为 0–255 的饱和度和亮度下限；`radiusPixels` 为原始分辨率小地图中的圆环半径，允许 3–100 像素。这些参数必须针对当前游戏、显示布局和角色标记校准，不能把其他绿色图形一概当成自己。

颜色圆环必须先与可靠的自己头像位置一致，之后只能在近期位置附近逐帧测量；它不能初始化身份或在长时间失去观测后单独恢复身份。检测检查圆环半径、颜色分布、至少三个象限的圆弧覆盖和候选唯一性；不满足条件时停止使用该辅助定位，不输出历史位置。连续帧仍可见的圆环可以延续自己位置，但队友仍须单独可靠识别，路线仍受障碍网格约束。分析的 `selfSource` 区分 `template` 与 `marker`；重新框选小地图或自己的头像会清除圆环配置。合成测试覆盖部分遮挡、当前位移、长间隔、多个圆环和无关图形的拒绝；这不等于真实对局中圆环识别或整局流畅性已通过验收。

`selfMarker.partialArc: true` 可显式启用实验性部分圆弧拟合，省略或设为 `false` 仍使用原检测。此时 `radiusPixels` 应校准为颜色环的**中线半径**，不能取外缘：本次原始小地图中线约 24 像素，旧配置的 26 像素偏向外缘。新检测按固定半径搜索当前完整小地图的颜色像素，要求连续至少 100°、至少两个象限的圆弧、内外颜色分布及全图原始竞争峰分差，再检查近期身份和位移；不会先裁去远处竞争者来制造唯一性。完整头像仍优先。它不能凭一段绿色圆弧初始化自己，可信观测的最大中断间隔为 1.5 秒（包括 basic 模式）；每次当前圆弧成功测量可延续身份，失去当前像素或时间倒退时不输出旧坐标。默认三象限检测的其他配置和行为保持兼容。

离线验证中，开发版 221 的同一录像有 306 个战斗帧：原先 49 帧自己定位缺失，启用部分圆弧后恢复其中 12 帧，剩余 37 帧；原有可靠帧无回退，新增位置中仅 2 帧最终产生方向，不能把位置恢复数当作移动次数。246 个完整头像对照的圆心与模板中心差 P95 为 2.55 像素；173 张真实结算图、285 张移除当前自己圆环的构造图均未产生候选。随后冻结参数回放另一场动态训练片段的 206 张已采图像（实际停止于第 207 帧），自己定位缺失从 97 降至 82，新增恢复 15 帧，原可靠帧无回退；长时间完全遮挡仍未解决。这些是本机离线图像回放，未部署该开关进行实际整局控制，也不覆盖所有游戏中的同色无关圆弧或其他布局。

独立可选的 `targetRing` 配置结构为 `{ hueMin, hueMax, saturationMin, valueMin, radiusPixels }`，用于完整目标头像及其跟踪候选的当前队伍颜色校验。原始头像匹配及候选竞争仍先于颜色校验，不能先筛掉其他颜色的竞争者来制造唯一性。候选须同时通过既有头像门限、当前蓝色圆弧至少 40% 支持及连续至少 80° 的圆弧，且完整外圈中的红色像素比例不超过 15%，才接受并更新跟踪历史；历史位置不能代替本帧颜色证据。它不启用部分头像识别、不要求顶部存活提示，也不强制全帧，兼容小地图 ROI。省略 `targetRing` 但已显式配置 `targetPartial` 时，完整头像颜色校验使用 `targetPartial.ring`；两者均未配置时保留原有行为。

`targetRing` 的色相使用 OpenCV 0–179 范围，饱和度和亮度下限为 1–255；`radiusPixels` 为原始小地图像素中的 5–100，采样半径为该值 ±2 像素，最内侧须在头像模板外侧。本次私有样本的 41 × 41 像素头像采用 `hueMin: 85`、`hueMax: 130`、`saturationMin: 100`、`valueMin: 100`、`radiusPixels: 25`；这些不是通用默认值，须按实际游戏、分辨率和头像颜色重新校准。局部静态图像验证不代表动态跟随或敌我身份识别已全面验收。

实验性 `targetPartial` 默认关闭，可通过 CLI 配置显式启用，用当前帧仍可见的半张或四分之三头像重新确认目标。配置结构为 `{ ring: { hueMin, hueMax, saturationMin, valueMin, radiusPixels }, alive: { portraitTemplate, portraitRegion, healthBarRegion } }`。`ring` 使用 OpenCV HSV 范围，色相为 0–179、饱和度和亮度下限为 1–255，半径为原始小地图像素中的 5–100；检测采样半径为该值 ±2 像素，最内侧也须位于头像模板外侧。沿用的 `targetTemplate` 必须为 9–129 像素奇数边长方形。`alive` 的头像和血条必须属于同一目标：`portraitTemplate` 为顶部彩色头像的 PNG base64，最多 256,000 字符，解码尺寸须与 `portraitRegion` 一致；两个区域均为完整屏幕内的归一化矩形。头像区域至少 12 × 12 像素、血条区域至少 3 × 3 像素，实际还须满足彩色头像及横向蓝血条检测。更换目标、布局或分辨率后必须重新校准。这项配置强制请求完整原始画面；裁剪帧不能代替顶部存活提示。

部分身份门限固定：总体匹配至少 0.97、每个使用的象限至少 0.95，与全图所有原始形状候选的分差至少 0.04；不能先筛掉颜色或象限不合格的竞争者来制造唯一性。候选中心的可见身份象限还须有至少 40% 蓝色圆弧支持及连续至少 80° 的圆弧。顶部头像须仍匹配并保有颜色，校准血条须可见。每帧均检查这些证据，严格连续三帧、总跨度不超过 3 秒，且相邻时间和位移符合新鲜度及运动限制后才接受；任一身份、圆弧、存活提示或图像校验失败都会清空确认历史。没有当前观测时不返回历史坐标，也不通过跳过失配帧凑足三帧。

完整头像匹配仍优先，只有本帧完整匹配失败时才使用通过上述门限的部分头像位置；完整匹配本身不能替代部分身份的三帧证据。分析结果 `targetSource` 区分 `template`、`partial` 与 `labels`。自己的可靠定位、路线、跟随距离、原有运动确认和输入时限继续生效，出现 `partial` 不等于已经发送方向。这项能力不能恢复完全不可见的头像，当前蓝弧也不能排除所有邻近友方头像污染的情况。

实验性 `cameraAssist` 与 `selfCameraAssist` 均默认关闭，仅可通过 CLI 配置显式启用，需要 App 模式和开发版 226 起提供的 `cameraFrameProvenance=1` 能力；主机在开始时检查该能力，旧 App 或 basic 模式会拒绝。任一配置都会强制请求完整原始画面，并显式协商截图来源证明。`observe` 不发送任何触控，也不会自行按住小地图来建立相机视角。

配置对象的字段如下。这里部分数值采用原始像素，不能沿用一般跟随参数的归一化单位。

| 字段 | 含义与单位 |
| --- | --- |
| `referenceWidth`、`referenceHeight` | 校准时完整屏幕的原始像素宽高，必须与主配置 `width`、`height` 一致。 |
| `targetLabel`、`healthBarTemplate` | 当前指定队友的准确名字、完整蓝色血条外框截图，均为 PNG base64；血条可以缺血，不能只截剩余蓝色填充。 |
| `team` | `cameraAssist` 可省略或显式设为 `blue`；`selfCameraAssist` 必须显式设为 `green`。 |
| `region` | 在完整屏幕中搜索名字的 **归一化矩形**。 |
| `healthBar.width`、`height` | 完整血条模板的原始像素宽高。 |
| `healthBar.offsetX`、`offsetY` | 从名字模板中心到完整血条外框左上角的原始像素偏移。 |
| `matrix` | 3 × 2 仿射矩阵，把主画面名字中心的原始像素坐标转换为相对相机按住点的小地图原始像素位移。 |
| `anchorBounds` | 允许使用上述投影的**名字中心**范围，以完整屏幕原始像素表示；它不是相机按住点的范围。 |
| `projectionErrorPx` | 镜头放置时预留的投影误差，单位为原始小地图像素，默认 3；不能用它代替投影校准。 |

投影关系为 `目标小地图原始像素位置 = 已证明生效的相机按住点 + [名字中心X, 名字中心Y, 1] × matrix`。结果还必须位于校准的小地图内。名字、完整蓝血条外框与偏移、矩阵、有效名字中心范围必须针对当前目标、分辨率、布局和镜头行为单独校准；不会自动缩放或重新拟合。当前帧须有唯一的准确名字和相符的完整蓝血条外框，红色血条、外框断裂或歧义会拒绝。校准及负样本覆盖不足时，不能以相机当前对着某个头像堆为由推定目标就在其中。

`selfCameraAssist` 使用相同字段结构，但其中 `targetLabel` 表示**自己**的准确名字，血条模板及 `team: "green"` 对应自己；名字、血条偏移和投影范围须独立校准，不能直接复制队友模板。自己和队友在同一当前截图、同一已验证相机证明下分别定位；分析结果用 `selfSource=camera` 或 `targetSource=camera` 标明各自来源。只有本帧双方位置都可靠，并通过路线及原有确认时才可移动。这一入口及镜头重新居中仍属实验性能力，尚未证明真实自定位遮挡恢复或整局跟随效果。

小地图目标丢失后，主机只在最近 3 秒内仍有可靠完整头像位置时，才用该位置选择短暂搜索镜头；启用自己辅助后，当前队友可靠而自己缺失时，也可按自己最近 3 秒内的完整头像或经过既有身份校验的颜色环位置搜索。自己颜色环必须显式来自本帧 `selfSource=marker`，与当前可靠自己坐标一致，且比已有搜索起点更新，才能替换该历史起点；同帧完整头像仍优先。颜色环不提供完整头像速度，相机定位也不能反过来更新搜索历史。镜头放置按相应校准的 `anchorBounds` 中心与矩阵计算，使预计名字落在已验证投影范围内，越界或几何不成立时拒绝按压。旧位置只用于选择镜头，不作为当前位置发送摇杆方向。相机保持与摇杆使用同一会话、同一个 touch 数组：`id=1` 为相机，`id=0` 为摇杆；首次按住相机时松开摇杆。

已启用 `cameraAssist` 或 `selfCameraAssist` 时，初始搜索可仅对镜头触点 `id=1` 使用短时领先预测：速度来自相邻两帧当前完整头像，间隔须不超过 1.5 秒，最新完整头像证据须不超过 1 秒；部分头像、相机定位和自己颜色环不用于这项速度估计。预测时长按毫秒计算为 `min(1000, fullAgeMs + max(250, intervalMs, captureMs))`。预计角色位置或镜头点越出小地图时放弃预测，回到原合法镜头放置，不把越界点截到边缘；原放置也不合法时仍拒绝。预测不写入当前角色位置、不用于摇杆 `id=0` 的方向，当前帧、TTL、镜头证明和搜索期限检查保持不变。`camera.placement.prediction` 记录是否采用、原因、证据年龄、预测时长、速度、样本间隔及观测点/预计点。相关 62 项相机 Node 回归通过，尚未以真机动态跟随验证这项领先行为。

初次搜索最多 6 秒；当前有效镜头证明下的名字及相应颜色血条，或双方均不依赖镜头的当前可靠观测，可以刷新搜索期限，使持续有效的镜头跟踪超过 6 秒。仅启用队友辅助时，当前完整目标头像也可续期；启用自己辅助时，仅有完整队友头像不足以延长自己缺失的搜索。缺少任一必要的当前可靠位置时立即松开摇杆；最后一次有效证据之后最多再搜索 6 秒，随后释放且清空历史。回执、镜头证明本身、旧坐标均不能延长搜索。每条指令 TTL 仍最多 1,200 ms，接近搜索期限时缩短；截图时效与证明检查不变。当前镜头识别接近校准范围边缘时，可依据本帧位置及相邻当前观测的速度重新居中；换点后的下一帧必须取得新点已稳定生效的证明，不能沿用旧镜头上下文。目标完整头像经过多帧稳定确认，且自己也不再依赖镜头时，才延迟释放 `id=1`，保留该帧经双方定位及路线检查得到的有效摇杆指令。

搜索期间，队友完整头像恢复而自己仍缺失时，可转为搜索自己；自己恢复当前可靠的非相机定位而队友仍缺失时，也可转为搜索队友。后者必须已启用 `cameraAssist`，且最近 3 秒内有完整队友头像位置；只启用自己辅助时不会启动队友搜索。切换只改变 `id=1` 的搜索角色，立即停止 `id=0`，沿用原搜索截止时间及 TTL 规则，不重启 6 秒预算；换点后仍须取得新点已生效的当前帧证明。自己颜色环历史与双向角色切换已通过逻辑和模拟手机 I/O 回归，真实动态效果仍待验证。

跟随状态中的可选 `camera` 记录当前计划状态及原因、镜头点、最近回执序号、已验证帧的 `frameProofSequence`、保持时长、证据年龄、搜索及触控 TTL 剩余时间，以及 `armAttempts` / `recenterAttempts` / `releaseRequests` / `releaseReasons` 累计值。`role` 表示当前镜头放置主要服务于 `target` 或 `self`，不限制同帧另一方识别；`frameSelf` 区分完整头像、其他当前位置、镜头位置和缺失，`placement` 记录按压、保持、重新居中或拒绝的计划及范围判断。其中 `placement.seedSource` 的 `full` / `marker` 标明搜索起点使用的历史证据，不表示该帧已经定位到角色。它们是电脑端诊断，不证明手机当前仍按住触点，也不会续期。释放计数表示提出释放的原因，实际结束仍以受管手机会话结果为准。

触控 `acceptedSequence` 只是接收回执，不表示已经按下。Android 在手势完成回调后记录生效状态；同点续期保留 `epoch` 与 `heldSinceUptimeMs`，换点、释放、取消或过期会使证明失效。截图请求前后须仍是同一已生效触点，实际 `ScreenshotResult` 的手机单调时间必须在该稳定状态和有效期内。`cameraProof` 的 `epoch`、`sequence`、`x`、`y`、`heldSinceUptimeMs`、`capturedAtUptimeMs`、`expiresAtUptimeMs` 随同一张不可变图像及其分块保留，不因编码或下载延长有效期；手机 uptime 不能与电脑时钟直接相减。

主机只接受与最近成功回执的序号和点位一致、相机已稳定至少 250 ms、时间递增的本帧证明，再把相机上下文交给视觉模块。触控发生在截图之后，因此本帧只能证明前一次已生效的相机保持；刚发出的 hold 或视角归位帧不能当作已按住后的画面。截图加分析必须少于 1 秒才允许基于该帧输入；证明缺失、过期或变化时不使用相机方向。停止、暂停、恢复连接及结果不明的输入都会清除相机上下文并要求释放，不重放旧动作。这些门限和回归测试不代表真实游戏中的相机辅助已经通过整局验收。

CLI 的 `camera-sample` 用于采集一次指定点的镜头按压证据。先依据当前完整截图人工选择小地图中的点，再传入完整屏幕的整数原始像素 `--x` / `--y`，不是归一化坐标。它不会自动挑选队友，也不能证明点选位置对应指定英雄、游戏已经切换镜头或投影校准正确。`--output` 必须指向尚不存在的新目录；CLI 将其转换为绝对路径，不覆盖已有目录。

采样使用独立的 App 控制会话，检查 `cameraFrameProvenance=1`，先读取原始画面尺寸，再仅按住 `id=1`，不操作摇杆。收到回执后等待 450 ms，获取一张同序号、同点位、至少稳定 250 ms 的完整原始 JPEG；从发出按压到收到完整帧必须少于 1,200 ms，期间分辨率和会话须保持一致。随后尝试释放镜头并结束自有会话；任何验证、释放或结束失败均不发布样本，不重拍或重放按压。成功时新目录包含未经缩放的 `sample.jpg` 和 `sample.json`，后者记录图像 SHA-256、尺寸、触控回执、同帧 `cameraProof` 与主机分段耗时，供后续人工核对及独立校准使用。

该入口与相机控制器已通过统一 **67 项 Node 回归**：采样器 14 项、控制器 19 项、跟随集成 5 项、既有跟随 29 项。桌面构建 `dc248dd9fd770272` 已独立启动并确认启动 shell 退出后仍存活。2026-10-23 在 RMX3700、开发版 227 的训练画面完成三次真实 CLI 采样，触控发出至完整原始 JPEG 接收分别约 1,156、1,018、904 ms，均携带匹配的手机证明并完成释放和会话结束。第二张图中目标已离开原位置，视觉校验拒绝用于标定；采样成功不等于目标识别或投影正确。其余 Node 测试使用模拟手机 I/O，不能据此声称整局跟随通过。

序列始终使用同一个受管会话，只发送镜头 `id=1`，不发送摇杆 `id=0`。`continue` 必须在前次保持仍有效时发出并收到回执；过期或结果不明时停止后续步骤，不隐式改成重新按下、不重放。后续 `release-newdown` 先显式释放，等待超过前次保持的过期上界及保护间隔，保存释放后的原始截图，再重新按下；释放图仍有 proof 时拒绝继续。只对这一有限序列使用 **1,500 ms** 保持时限，收到回执后的等待仍为 450 ms，截图 proof 仍须证明同序号、同点位且已稳定至少 **250 ms**。普通单张 `camera-sample` 和自动跟随的 **1,200 ms** 输入寿命不变。

新目录先写 `plan.json` 固定步骤，再保存完整原始 JPEG 及元数据：`baseline.jpg` / `baseline.json`、各 `step-NN/sample.jpg` / `sample.json`，重新按下前另有 `release.jpg` / `release.json`。`sequence.json` 记录步骤状态、触控与采集事件、已保存文件、失败和清理结果；中途失败仍保留已取得的诊断文件，并明确标记 `complete=false`，不能把部分结果当成完整对照。图像不缩放、不改编码字节，元数据包含尺寸、SHA-256、手机 proof 和主机耗时。

`complete=true` 和单步 `valid=true` 只表示协议检查及采样完成，**不证明游戏响应了 MOVE、镜头已经到达目标点或冻结投影正确**。释放图没有 proof 也不代表游戏已归位。验收必须独立核对当前白色视野框、静态场景与角色名字的位移，并保持原有矩阵、域和门限；出域样本只能用于诊断，不能事后扩域后算通过。

首轮真机序列使用原 1,200 ms 时限，在第 2 步连续移动回执到达时超过前次保持期限约 **29.6 ms**，因此停止后续步骤并完成释放及会话结束，没有第 2 步截图。首步冻结自己矩阵的投影误差约 **0.75 px**，只提供单点证据；本轮不能判断 8 px MOVE 是否被游戏执行，也不能宣称八步对照或新的 1,500 ms 序列实测通过。

后续静态八步真机对照采用 1,500 ms 时限，关闭 AI 与兵线，保持角色不动。八张图中的当前完整自己头像位置均为原生小地图坐标 **(251,308)**；全部协议采样有效、proof 稳定时间为 410–522 ms，序列正常完成。对照继续使用冻结的自己矩阵、原有名字域及门限，实际大位移选用 **−20 px**，与上方说明性示例的 −24 px 不同。

在 A=(261,307) 连续移动至 B=(253,307) 时，Android proof 的点位和 epoch 已更新，但当前名字锚点与白色视野框均没有位移；冻结投影误差为 **8.433 个原生小地图像素**，该步失败。释放后重新按下同一组 A、B，名字锚点向右移动 **255 个屏幕原始像素**，白框向左移动 **7.5 个小地图原始像素**，B 点投影误差为 **0.505 px**。三张重新按下前的释放图均确认白框消失、镜头归位及自己的绿色血条可见，证据不只来自 proof 缺失。这一对照显示，系统手势完成和新 proof 不能直接证明游戏执行了连续 MOVE。

连续大位移 −20 px 确实改变了视角，按名字位移与冻结矩阵换算约为 **−22.005 px**，白框实际位移为 −21.5 px；返回 A 后白框仍偏右 **2 px**，名字锚点 X=994.5，落在原域左界 1000 之外，因此该步保持出域拒绝，没有扩域或修改阈值后计为通过。八步采集完成不等于八步几何验证通过，也不代表动态跟随修复通过。随后主机加入 `cameraPointChange="release-newdown"` 能力检查；手机端换镜头点时释放再按下、同时保留摇杆触点的实现仍需单独构建和实机复验。采用该新策略后，序列的 `continue` 只表示主机未显式释放，实际底层是否重新按下还须结合报告中的 `nativeCameraPointChange` 判断，不能与本轮旧策略的连续 MOVE 混为同一种对照。

状态中的 `timings` 提供最近一次截图耗时 `captureMs`、视觉处理耗时 `analysisMs`、输入请求耗时 `inputMs`、心跳检查完成耗时 `heartbeatMs` 和相邻心跳检查完成间隔 `heartbeatGapMs`，单位均为毫秒。这些是电脑端观测的耗时，用于区分截图/传输、识别、输入及心跳延迟，不代表手机内部各阶段的独立测量；尚未完成的阶段可能没有值。若迟到的 `sync` 失败被同一连接上更新的认证响应取代，检查也会完成，但不代表手机实际收到了该次 `sync` 或续期成功。排查会话到期时，应同时核对 `connection-events.json` 中的 `superseded` 记录及手机日志，不能仅据这两个心跳计时字段判断手机租期。

电脑端调度诊断也放在 `timings` 中：`heartbeatTimerLagMs` 是最近一次心跳定时器相对 1 秒间隔的迟到时间，`maxHeartbeatTimerLagMs` 是本次运行的最大迟到时间；`eventLoopMaxDelayMs` 是以 20 ms 分辨率采样得到的本次运行事件循环延迟累计最大值，以上均为毫秒。它们与等待手机响应的 `heartbeatMs` 含义不同。

`slowAdbStarts` 最多保留本次运行开始以后桌面进程中最近 8 次同步启动路径总耗时至少 100 ms 的 ADB 调用，包括可执行文件定位 `resolveMs` 和启动调用返回前的 `spawnMs`；不把子进程随后异步执行命令的时间计为同步启动耗时。每项还包含记录时间 `at` 和命令类别 `operation`，不保存完整参数、设备标识或凭据。记录可能来自设备轮询等同一桌面进程的其他 ADB 工作，须结合时间及类别判断关联，不能直接归因为当前手机的一次输入。

`httpRequests` 最多保留本次运行开始以后桌面进程中最近 12 条已结束的手机 HTTP 请求，包含正常完成和错误结果。`socketMs`、`connectedMs`、`sentMs` 分别记录分配 socket、本地 TCP 连接建立和请求在本地写入完成的时点；连接对端是本机 ADB 转发端口，`sentMs` 不证明手机已收到请求。`headersMs`、`firstDataMs`、`endMs` 分别记录响应头、第一段正文和正文读取结束；所有这些值及 `totalMs` 均为相对请求开始的累计毫秒数，阶段耗时需取差值。`outcome=complete` 只表示响应已读取并解析为 JSON，不代表手机业务操作成功。记录还包括起始时间 `at`、请求类别 `operation` 和响应字节数 `responseBytes`，不保留路由、凭据、正文或错误文本。手机开发版日志中的 `headersRead`、`bodyRead` 则分别标记手机读完请求头和正文的累计时点，两端应比较各自时钟下的耗时，不能直接相减绝对时间。

### Android 持续触控回归

Android 的续接手势若只有不变的触点、没有按下、移动或抬起事件，会被判为失败。保持摇杆方向时应保留已经按下的触点，等方向变化再续接；本地仍每 80 ms 检查会话授权和指令有效期，到期或停止时提交抬起。坐标统一取整，避免亚像素变化在 Android 内部取整后变成空手势。对应系统行为见 [Android 13 MotionEventInjector](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android13-release/services/accessibility/java/com/android/server/accessibility/MotionEventInjector.java)。

`FollowTouchTest` 使用开发版的本地空白测试页面，检查持续按住、转向、主动释放、指令过期与撤销授权。先运行 `node scripts/build-phone.mjs --instrumentation`，安装开发版和测试 APK，再由测试宿主执行该测试类。测试需要已授权且实际运行的无障碍服务，不会修改系统权限。Instrumentation 会重启配套进程，测试宿主必须恢复连接；不要把受管命令因 App 重启而断开误报为测试成功。本次经用户明确授权使用 ADB 等待 instrumentation 完整结果，并通过 `ppilot phone connect` 和 `accessibility-repair` 恢复服务；不能因此为其他任务推断原生 ADB 授权。

### 2026-10-23 中断排查与后续验证

中断不能全部归为同一原因。电脑的 ADB 日志显示，前一轮失败前在 10 月 22 日 22:51:36.694 出现 TLS `SSL_read` 零字节和 `connection terminated: read failed`，22:51:37.051 又握手成功；23:23:20 的另一次故障也有同类记录。约 0.3–0.4 秒的无线 ADB 传输中断会使原端口转发失效，随后访问旧本地端口才出现 `ECONNREFUSED`。手机配套 App 实例和电脑 ADB 进程未重启，桌面的设备轮询可能错过如此短的掉线。已定位到传输中断这一层，但触发 TLS 断开的手机或网络原因仍未确定，不能宣称无线链路已修复。

另一个独立问题在 ProfilePilot 的跟随保活：原来的每秒 `pulseWrapper` 仅更新电脑端任务状态，手机端 8 秒会话租期依赖全局设备轮询发送 `sync`。全局轮询被拖慢时，即使跟随循环还在工作，手机也可能将会话标为 `disconnected`。后续一轮在 119 帧、52 次方向更新后结束，手机进入该状态，未找到同期新的 ADB 断线记录；这与上述会话超时路径相符，但缺少当时完整手机日志，不能把该次触发条件全部视为已证实。现在跟随任务独立发送 `sync`，并保留会话失效即停止的行为。

同时修复了旧后台轮询失败可能覆盖较新成功状态的问题：仅当同一转发上存在更新且足够近的认证响应时，允许用它取代过时的后台观测失败；输入结果不确定或缺少近期成功证据时仍撤销控制。迟到的旧轮询也不能删除已经替换的转发。最多 64 条本地 `connection-events.json` 记录保留故障时间、方法、会话阶段和短错误摘要，不记录请求正文、画面或认证令牌，用于区分首个故障与后续端口错误。

### 2026-10-23 完整截图分块与预览互斥修复

手机 App 的原始尺寸 PNG 截图新增分块协商：一次截图生成不可变结果，随后通过同一会话认证分段取回，每段最多 48 KiB 的 Base64 字符，传输有效期为 15 秒。桌面逐段核对传输 ID、偏移、长度、结束标记及当前会话；暂停、换代、过期或分块不完整时丢弃整个结果，不返回半张图，也不自动重新截图。未协商分块的旧响应仍可按原有截图结构返回。这个路径处理 App 截图响应，不改变小地图 ROI 请求，也不把侧栏的原生 ADB 截图改为 App 分块传输。
